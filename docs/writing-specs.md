# Writing specs

## Layout

| File                          | What it is                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------ |
| `specs/<name>.ts`             | A spec in TypeScript. tla-ts compiles it to `specs/<Name>.tla` and `.cfg`.     |
| `specs/<Name>.tla` and `.cfg` | Generated from the TypeScript. Commit them; never edit them.                   |
| `specs/<Module>.tla` and `.cfg` | A hand-written TLA+ module. It has no "Generated by tla-ts" header.          |
| `specs/<name>.mutants.mjs`    | Mutants for a spec or module (see below).                                      |
| `specs/lib/*.ts`              | Types and helpers imported by specs. Not checked on their own.                 |

`npm run check` checks every spec and module, then every mutant, then mutant coverage. `npm run check -- defer` checks only names that contain `defer`.

## Mutants

A property that no bug can break proves nothing. Every invariant and temporal property must be caught by at least one mutant, or `npm run check` fails.

A mutant is a copy of a spec with one realistic bug planted:

```js
// specs/defer.mutants.mjs
export default [
  {
    name: "propagates a deferred field error past the fragment boundary",
    find: 'errors.add("profile");',
    replace: 'errors.add("profile");\n    data.me = "null";',
    property: "dataIsNeverRetracted",
  },
];
```

- `find` must occur in the file. The first occurrence is replaced.
- `property` is the one property that must catch the bug. The check runs the mutant with only that property enabled, so the property catches it on its own and a different property can't take the credit.
- `file` (optional) is the file to mutate, by default `<name>.ts`. `module` (optional) is the hand-written module to check instead of the mutated spec, for example a conformance module that extends a generated one.

A good mutant is a bug someone could plausibly write. It is not a negation of the property. If the only way to break a property is to delete the guard that enforces it, the property restates the code. Either drop it or replace it with one that states an outcome.

## tla-ts's TypeScript

See [tla-ts's guide](https://github.com/aidenybai/tla-ts/blob/main/docs/typescript.md). These points come up in practice:

- **Comments:** write header comments as `/* … */`. tla-ts reads JSDoc tags, so a `/** … */` comment that mentions `@defer` or `@stream` fails with "Unknown tag".
- **Record keys** must be TLA+ identifiers: `userId`, not `"user.id"`.
- **Nondeterministic initial values:** `let variant!: "a" | "b";` starts in every value of the type. The `!` silences TypeScript's use-before-assignment error.
- **Values of different types:** TLC can't compare them. Comparing a string with a record, or an integer with a string, stops the check with an error. Give every value of a union the same shape, for example `{ kind, type, length }` for each variant, and use strings for path segments, `"0"` rather than `0`.
- **No loops:** use recursion with `slice` or an index, plus `every`, `some`, `filter`, `map` and `find`. `new Set(s.values().filter(f))` builds a set. TypeScript has no `.size` on an iterator, so use `difference` and `intersection` to count.
- **Parameters:** an action may take any parameter type if a guard picks it from a set first: `if (!running.has(path)) return;`. A later guard may depend on an earlier one: `if (!choicesFor(path).has(outcome)) return;`.
- **`@fair`:** weak fairness for each value of a parameter whose type is finite, such as a string union. For a parameter with no finite type, such as a path picked by a guard, it is weak fairness of the whole action: some choice is eventually taken.
- **`@terminating`:** mark a predicate `@terminating` for states where it is fine that nothing can happen. Without it, those states are deadlocks.
- **`@always`:** properties take `before` and compare the previous state with the current one. Prefer them to "flag" variables for statements about change, such as no retraction.
- **Actions that call recursive helpers:** compute everything first, then assign. Once an action has assigned a variable, later reads must see the new value, so tla-ts inlines any helper called after that point. Inlining a recursive helper overflows the compiler's stack (`RangeError: Maximum call stack size exceeded`). Read into `const`s before the first assignment.
- **Recursive helpers as callbacks:** don't pass one by name, as in `.map(jsonOf)` inside `jsonOf`, which overflows the stack too. Write `.map((c) => jsonOf(c))`.

## tla-ts's TLA+ checker

- **Mutual recursion:** declare every operator in a recursive cycle in one `RECURSIVE` line, including ones that don't call themselves (`CompleteFields` in `Reference.tla`).
- **Recursive operators under `[]`:** a temporal property `[](P(vars))` whose `P` reaches a `RECURSIVE` operator overflows the checker's stack while it works out the formula's level. State it as an action property instead, `[][P(vars')]_vars`, which says the same of every state after the first; `RootFieldsAreSerial` in `ExecutionConformance.tla` does this.

# The coerce area

`graphql-tla run coerce` checks input coercion: how an implementation turns variable values and argument literals into the arguments a resolver gets, and when it refuses them. It also checks which operation a request runs. The reference is [`specs/Coercion.tla`](../../specs/Coercion.tla), written from the September 2026 edition, which the kit grades (see [Editions](#editions) for October 2021 and September 2025). It covers:

- §2.10.4, the Unicode text of string literals (escapes and block strings), from [`specs/Lexer.tla`](../../specs/Lexer.tla), and lexing that only an argument's value shows (commas, comments, number tokens next to each other, float exponents);
- §2.2 descriptions and comments, which mustn't change the response; §2.3, a document with a type system definition isn't executed; §2.7 and §2.10.8, arguments and input fields in any order; a document that doesn't parse (§6.1, §7.1.6), from [`specs/Parser.tla`](../../specs/Parser.tla);
- §3.5.1 to §3.5.5, the built-in scalars;
- §3.9 enums, §3.10 input objects, §3.10.1 OneOf input objects (new in September 2025), §3.11 lists and §3.12 Non-Null;
- §6.1 GetOperation, §6.1.1 validating requests, §6.1.2 CoerceVariableValues and §6.4.1 CoerceArgumentValues, on root fields and below the root (§6.4.4, capability `nested-fields`);
- §6.2.3.1 CreateSourceEventStream: the source stream's arguments, and an error establishing it, a request error since September 2026 (capability `subscription-source`);
- §6.3.2 and §6.3.3 branches only an invalid document reaches (a missing fragment, an undefined field, a second subscription root field), for adapters with `unvalidated`;
- §6, a request's `extensions` (informational, capability `request-extensions`);
- §7, §7.1.1, §7.1.3, §7.1.6 to §7.1.8: a response for every request, a map, the shape of request errors and of every error, and no other top-level entries.

```shell
npx graphql-tla run coerce --adapter "node adapters/graphql-js/adapter.mjs --graphql 17" --strict --report coerce.json
```

The area follows [the contract for areas beyond execution](../kit-areas.md).

## Request

```json
{"type":"coerce","id":12,"schema":"enum Color { RED GREEN BLUE } … type Query { … }","document":"query($x: Int) { int(v: $x) }","variables":"{\"x\": 2147483648}"}
```

- **`schema`:** SDL. Every vector uses the same schema, which has one root field per argument type, one mutation field, §3.10's `ExampleInputObject`, and `Settings`, an input object whose `Int`, `Float` and `Boolean` fields are all nullable with no default. The 20 OneOf vectors use the same schema plus §3.10.1's `ExampleOneOfInputObject @oneOf` and a field `oneOfExample` that takes it. Each root field returns a nullable `String`. The 19 vectors below the root (`nested-fields`) add `type Nested { int(v: Int): String  intNN(v: Int!): String  strict(v: Int!): String!  child: Nested }` and the root fields `nested: Nested`, `nestedNN: Nested!`, `items: [Nested]` and `itemsNN: [Nested!]`. The 18 subscription vectors (`subscription-source`) add `type Subscription { event(v: Int): String  eventNN(v: Int!): String }`.
- **`document`:** one or more operations, each selecting one root field (or, for the vectors below the root, one path of fields), or no operation at all. It may also hold descriptions, comments, type system definitions, or not parse at all: a document that doesn't parse must be answered with the implementation's own request error, not an `error` message (see [Result](#result)).
- **`variables`:** the request's variables as **raw JSON text**. Parse them with your implementation's own JSON parser, as a server would. Some vectors depend on that parser (see [Big numbers](#big-numbers)).
- **`operationName`:** the operation to run. Absent when the request doesn't name one.
- **`subscribe`:** only on the subscription vectors (capability `subscription-source`): what the subscription root field's source stream resolver does, `"stream"` (return a stream of one event) or `"raise"` (raise an error). Only used when the selected operation is a subscription.
- **`extensions`:** only on the request extensions vectors (capability `request-extensions`): the request's `extensions` map as raw JSON text, such as `{"graphql-tla": true}`. Pass it to the implementation as the request's extensions, where it has a place for them, as a server would; otherwise parse it and drop it.

Build the schema with a resolver on every field that records its path and the arguments it got, and returns a non-null value: for a leaf, any value (`"ok"`); with `nested-fields`, for a field of an object type an object (`{}`), and for a list of objects a list of two (`[{}, {}]`). Then execute the document, as your implementation would execute a request. With `subscription-source`, a subscription operation goes through the implementation's subscribe entry point: give the subscription root fields a source stream resolver that records its call (field name and coerced arguments, in `sourceCalls`) and then returns a stream with one event (`"stream"`) or raises (`"raise"`). The response is the first result of the response stream, or the result the subscribe entry point gives instead of a stream. Close the stream after its first result. In an engine where the event is the root field's value, no resolver runs on the event, as in graphql-java and Hot Chocolate (see `subscription` under [execution's Capabilities](../conformance.md#capabilities)). There the event stands for the root field's resolution: when the source stream emits it, record the root field's call in `calls`, at its response path, with the arguments the source stream resolver got. Other operations are executed as usual, whatever `subscribe` says.

## Result

The adapter sends back what happened, and the kit decides what it means:

```json
{"type":"result","id":12,"response":{"data":{"int":"ok"}},"calls":[{"path":["int"],"arguments":{"v":2}}]}
```

- **`response`:** the execution result, as your implementation would serialize it: `data` and `errors` as they are.
- **`calls`:** one entry per resolver call, in order, at every depth. `path` is the field's response path (with list indices and response names), and `arguments` is the argument map the resolver got, as JSON:
  - Int and Float as numbers, String and ID as strings, Boolean as booleans;
  - enum values as their names;
  - lists as arrays, input objects as objects;
  - an argument or input object field that has no value is left out;
  - a value that JSON can't represent, such as a non-finite float, as a string (`"Infinity"`).

- **`sourceCalls`:** with `subscription-source`, one entry per call of a source stream resolver: `{"field": "event", "arguments": {"v": 1}}`, the field's name (not its alias) and the coerced arguments, in the same JSON form as `calls`. Leave it out or send `[]` when there was none.

Any other fields are ignored, but appear in the report's examples. A `response` that is there but isn't a map (a list, a string, `null`) is in the format: it fails `resultMap`. A result without `response` isn't.

**A document that doesn't parse** is answered with the response the implementation gives, as a server would: a request error with the parser's error (`{"response":{"errors":[{"message":"Syntax Error: …"}]},"calls":[]}`). If the implementation's parse function throws, catch its syntax error and put it in `errors`. An `error` message there is graded as no response, under `responds`.

**Variables the transport can't carry.** If the adapter's JSON parser can't read the variables at all because a string holds a lone surrogate (as Ruby's `JSON.parse` refuses `"\ud800"` written as an escape), answer `{"type":"result","id":12,"unsupported":"lone surrogate: why"}`. The kit doesn't grade the vector, and the report's provenance counts it under `skipped` ("unsupported by the adapter"), rather than crediting the implementation with an answer it never gave. The kit honours `unsupported` only where the vector's variables really hold a lone surrogate (19 vectors). Anywhere else it is graded as a crash. A run where nothing was graded fails.

**No response.** If the implementation produces no response at all, say because executing the request throws instead of returning a result, answer `{"type":"error","id":12,"message":"…"}`. The kit records the outcome "no response" and goes on ([the protocol](../kit-areas.md#protocol)). Only the message's first line reaches the report. Don't make up a response for it: an empty `response`, or a request error the implementation never produced, would be graded as something the implementation didn't do. Execution has a message of its own for this, `no-response`; the coerce area uses `error`, as parse, validate and schema do for a crash, so a `noResponse` field in a result is ignored like any other.

The kit classifies each result as one of five outcomes:

| Outcome | The result shows |
| --- | --- |
| request error (§7.1.3) | no `data` entry, at least one error, and no resolver call. A result with `"data": null` instead of no entry is also a request error, but fails `requestErrorNoData` |
| field error | `data` holding only the field, which is null, exactly one error, and no resolver call. The error's path should be the field's response path, `["int"]`. Another path, such as the argument's `["v"]`, or none, still makes a field error, but fails `fieldErrorPath` |
| value | `data` holding only the field, which isn't null, no errors, and exactly one resolver call, at that field. Its `arguments` are the coerced arguments |
| no response | the adapter answered with an `error`. It never matches an answer, not even a request error, since a request error is a response |
| other | anything else, for example a request error after a resolver ran. It never matches an answer |

A vector whose field isn't a root field the response holds under its own name (the vectors below the root, and the subscription vectors) has `at`: the field's name, its response positions (`paths`), and the data the reference gives when its arguments raise (`error`) or don't (`value`), with `"ok"` at the field. For those, a field error is data shaped as `at.error` (the same maps and lists, null where it is null), one error per position, and no resolver call at any position (the parents' calls are allowed); errors whose paths aren't exactly the positions still make a field error, but fail `fieldErrorPath`. Where the error reaches the root, `at.error` is null: `"data": null` with one error per position, each with a path, is the field error, and otherwise a request error with `"data": null`. A value is data shaped as `at.value` (any non-null leaf value), no errors, and exactly one call at each position, all with the same arguments. For a subscription whose source stream the reference creates (`sourceCalled`), the value also needs exactly one source call of the field with those arguments, or it fails `sourceStream`.

A response that isn't a map is "other", and fails `resultMap` whatever the vector.

A request error or field error whose errors aren't all maps with a string `message` (`[null]`, `{}`, `{"message": 1}`, or a field error with only a `path`) is still classified, but fails `errorFormat` wherever its outcome would otherwise pass (§7.1.6: "Every error must contain an entry with the key {"message"} with a string description"). A value whose response has `"errors": []` is still a value, but fails `errorsList`. A result with a top-level entry other than `data`, `errors` and `extensions` fails `additionalEntries`, and one whose `extensions` isn't a map fails `extensions`, in the same way (§7.1.8, §7.1.7).

## Capabilities

| Capability | Meaning |
| --- | --- |
| `coerce` | The adapter answers `coerce` requests. |
| `absent-vs-null` | `arguments` tells an absent entry from a null one. Without it, null and absent count as the same at a declared argument or input field whose type is nullable, and the vectors that only that distinction can tell apart are skipped. An entry that no argument or input field declares never matches, null or not. |
| `unvalidated` | The adapter executes a document without validating it. Without it, the kit takes the adapter to validate first, and grades the invalid documents under `invalidNotExecuted` or `onlyValidExecuted` (see [Validation](#validation)), except the 26 that are invalid only because a literal doesn't coerce (`literalOnly`): a request error passes there too. |
| `exact-numbers` | The adapter's JSON parser reads every number exactly. Without it, the vectors whose answer depends on how a parser reads big numbers are graded under the informational `jsonNumbers` check, not under Float or ID. |
| `nested-fields` | The adapter's resolvers return objects for object fields and two objects for lists of objects, and `calls` covers every depth (see [Request](#request)). Without it, the 19 vectors on the `nested` schema aren't sent. |
| `subscription-source` | The adapter takes `subscribe`, runs a subscription operation through its subscribe entry point with a source stream resolver it controls, and reports `sourceCalls`. Without it, the 18 vectors on the `subscription` schema aren't sent. Execution's `subscription` and `subscription-stream` are other capabilities, with another protocol. |
| `request-extensions` | The adapter takes `extensions` and passes it to the implementation as the request's extensions, or drops it where the implementation has no place for them. Without it, the 5 vectors with `extensions` aren't sent. |

## What is checked

Each vector's `expected` answer is `Coercion!ExecuteRequest` for the request. Where the spec permits more than one answer, or doesn't say which, the vector also lists the others. A result passes when its outcome, field and arguments match an answer that passes. Numbers are compared as numbers and keys in any order.

Each vector belongs to one check, by the outermost type its value meets. That is how the spec's own tables file their examples: §3.11 lists `[1, "b", true]` under List, and §3.10 lists `{ a: "abc", b: "123" }` under Input Objects. A variable with a default is filed under `variables` when the request leaves it out or sends null (the default is used, or null overrides it), and by its value's type when the request gives a value, as in the `variable` family. A vector whose expected request error comes from CoerceVariableValues also exercises `variables`, and one that expects a field error also exercises `arguments`. A field error where a request error is expected counts against `variables`. A request error where a field error is expected counts against `argumentErrorKind`, a SHOULD: §3.5 and §3.12 call a coercion failure a request error, and only "Any _request error_ raised as a result of input coercion during {CoerceArgumentValues()} should be treated instead as an _execution error_" turns it into a field error. The exception is the 4 vectors where §3.10 or §3.10.1 itself says "an _execution error_ must be raised" (`executionErrorRequired`: a variable in an input object literal whose runtime value is null at a Non-Null field, and a OneOf literal whose one entry is a variable with a null or no runtime value). There a request error fails the vector's own check. A list or input object vector rests first on the vectors that hold its items or fields on their own (see [Attribution](#attribution)).

### Attribution

One rule broken inside a list or an input object would otherwise fail every check whose type holds it: JSON `1.0` refused for Int fails `int` for `query($x: Int)`, but also `list` for `[Int]` and `inputObject` for `{"x": 1.0}` as a `Point`. So each list and input object vector names the `literal` or `variable` vectors that hold its items, its single value (which §3.11 wraps), or its fields, on their own (`restsOn`): `{"x": 1.0}` as `[Int]` rests on `{"x": 1.0}` as `Int`, and `{ points(v: { x: 1, z: 1 }) }` on `{ pointNN(v: { x: 1, z: 1 }) }`. If a vector fails its own check, and a vector it rests on fails its own check the same way (both reject, both accept, both produce no response, and so on), the failure counts where the inner vector's does, transitively. The finding says how many of its vectors came that way ("through an item or field that fails on its own"). If the inner vector passes, or fails another way, the failure stays with the list or input object rule: the implementation broke that rule itself. A failure of a cross-cutting check (`requestErrorNoData`, `fieldErrorPath`, `errorFormat`, `errorsList`, `resultMap`, `additionalEntries`, `extensions`, `argumentErrorKind`, `responds` and the validation checks) never moves.

The twins work the same way. A `descriptionsInert`, `syntacticOrder`, `requestExtensions` or `lexing` vector rests on the same request written without descriptions, in the written order, without extensions, or written plainly: if both fail the same way, the failure counts where the twin's does, since the rule broken is the twin's; if only the vector with the descriptions (or the reordering, the extensions, the unusual lexing) fails, it counts against its own check.

A vector whose answer depends on how the JSON parser reads a big number is `jsonNumbers`' for adapters without `exact-numbers` (see [Big numbers](#big-numbers)), except where a binary64 read gives a value the type must reject: `1e400` read as Infinity for ID. A value there is ID's failure (§3.5.5: "Any other input value, including float input values (such as `4.0`), must raise a request error"), so it counts against `id`, not `jsonNumbers`.

### Validation

For an adapter without `unvalidated`, the kit can't see from a response whether a request error came from the validator or from coercion, or whether the implementation's validator knew an invalid document was invalid. If the adapter also claims `validate`, the kit asks: it sends the vector's schema and document as a `validate` request ([validate](validate.md)), once per document, and takes the answer as the implementation's own validator's verdict.

- **An invalid document** (Validation.tla rejects it) that the implementation executes: §6.1.1 says "If validation errors are known, they should be reported in the list of "errors" in the response and the request must fail without operation execution". If the implementation's validator rejects the document, the errors are known, and executing it fails `invalidNotExecuted` (MUST). If the validator accepts it, the errors aren't known: the rule the validator misses is the validate area's to grade (at MUST), and executing the document fails only `onlyValidExecuted`, the SHOULD of "only operations from documents which pass all validation rules should be executed" (§6.1.1) and "execution should only occur for valid requests" (§5). Without `validate`, the kit can't tell, and grades the weaker `onlyValidExecuted`. October 2021 says the same.
- **A valid document** answered with a request error that the implementation's validator rejects: the request never reached coercion, so the failure isn't the coercion rule's. It fails `acceptsValid` (§5, MUST, as in the validate area), whatever the vector expects, even a request error. A request error the validator doesn't explain is graded as usual.
- **A document invalid only because a literal doesn't coerce** (`literalOnly`, 26 vectors, such as `{ int(v: 2147483648) }` and `{ float(v: 1e400) }`): §5.6.1 asks for literals to be "coercible", so a service may refuse it at validation or at coercion. Both a request error and the reference's field error pass. A resolved value fails the vector's own check, as it would without validation: `float` (MUST) for `1e400`, `intRange` (SHOULD) for an Int out of range, and `list` for a list of them, which moves to the item's check as usual (see [Attribution](#attribution)). For `{ float(v: 99999999999999999999) }` the rounded value also passes (`floatPrecision`).

Each check has the level of the sentence it grades in September 2026. Where a section mixes MUST and SHOULD, the check is split. Where the level is in doubt, the check takes the weaker one. Where an older release's wording gives another level, the check's `levels` in the report would say so (`{"September2025": "SHOULD"}`, say). No coerce check has one: September 2025 and October 2021 give every check the same level, and each `basis` quotes the older text where it differs. `oneOf` grades a rule that is new in September 2025.

| Check | Section | Level | What it covers |
| --- | --- | --- | --- |
| `stringValue` | §2.10.4 | MUST | A string literal's Unicode text: escape sequences, and a block string's common indentation, blank first and last lines and `\"""`. The static semantics have no key word, but they define the value §3.5.3 accepts. Only escapes and block strings that read the same in every edition are used. One vector, `{ string(v: "é😀") }`, holds a raw U+1F600, which October 2021's SourceCharacter (U+0009, U+000A, U+000D, U+0020–U+FFFF) leaves out when read literally, as the [parse area](parse.md) reads it: its `since` is September 2025, whose SourceCharacter is any Unicode scalar value. Expected texts come from `Lexer.tla`. |
| `int` | §3.5.1 | MUST | Int accepts only integer input values: not floats, strings or booleans. JSON `1.0` is an integer: §3.5's "they are interpreted as an integer input value if they have an empty fractional part (e.g. `1.0`)" has no key word, but it is a descriptive assertion, which Appendix A counts as a requirement; only the "e.g." is the example. Accepting an integer is CoerceVariableValues' and CoerceArgumentValues' step "If {value} cannot be coerced ..., raise a _request error_", otherwise coerce it. |
| `intRange` | §3.5.1 | SHOULD | Int rejects integers outside the signed 32-bit range |
| `float` | §3.5.2 | MUST | Float accepts integer and float input values, and rejects non-finite values ("not representable by finite IEEE 754 (e.g. {NaN}, {Infinity} ...), a _request error_ must be raised") and other kinds. The literal `1e400` is graded for every adapter (see [Validation](#validation)). |
| `floatPrecision` | §3.5.2 | INFO | An integer a double can't hold exactly, for Float: refused, or rounded to the nearest double. The sentence's "a value outside the available precision" isn't defined, and can't mean every value without an exact double (`0.1` has none and is rounded everywhere). The reference refuses such an integer by default; its `floatRounded` reading rounds it. Both pass, and the report's `observed` records which happened. It never fails the run. |
| `string` | §3.5.3 | MUST | String accepts only strings. A JSON string with a lone surrogate is `loneSurrogates`'s. |
| `boolean` | §3.5.4 | MUST | Boolean accepts only booleans |
| `idCoerced` | §3.5.5 | SHOULD | Strings and integers are coerced to ID. An ID made from an integer may use any format that writes the integer's exact value: `"1e+21"` and `"1000000000000000000000"` both pass for 10^21. |
| `id` | §3.5.5 | MUST | ID rejects everything else, including floats ("Any other input value, including float input values (such as `4.0`), must raise a _request error_") |
| `enum` | §3.9 | MUST | Enum literals of the enum's own values; not string literals, and not unknown values. Taking a JSON string as an enum value is a MAY, so a value and a request error both pass. |
| `inputObject` | §3.10, §3.12 | MUST | An object with only defined fields, required fields, and variables in fields. A nullable field with no default that is left out gets no entry ("Otherwise, if the field is not required, then no entry is added to the coerced unordered map"): `Settings` holds `{}` for `{ settings(v: {}) }`, not `0`, `0.0` or `false`. For a missing Non-Null field, §3.10 says "an error should be raised", but §3.12 says that if "an argument or input-object field of a Non-Null type is not provided ... then a _request error_ must be raised": both are normative prose about the same case, and accepting the value breaks §3.12's MUST. Those vectors cite §3.12. |
| `inputFieldDefaults` | §3.10 | SHOULD | An omitted input field gets its default value. The SHOULD applies to each field: a result that is right except for leaving out some or all of such defaults fails this check, not `inputObject`. Every entry the result does have must still be right. |
| `oneOf` | §3.10.1 | MUST | New in September 2025; September 2026 says the same. "exactly one entry and that entry must not be null or the null literal, otherwise a request error must be raised", and the coerced map "must contain exactly one entry and the value for that entry must not be null, otherwise an execution error must be raised": §3.10.1's table of examples and six more, all `since` September 2025, on the OneOf schema |
| `list` | §3.11 | MUST | Each item coerced, a single value wrapped in a list (recursively), variables as items. An item that isn't a list, where the item type is a list, becomes a list of one, in every edition (see [Editions](#editions)). For an item that is a variable with no runtime value, the spec doesn't say what happens, so null, a field error and the item left out all pass; for a variable item whose value isn't a list, where the item type is a list (only in an invalid document), the value as it is and the value wrapped in a list both pass (see [Readings](#readings)). |
| `nonNull` | §3.12 | MUST | The literal null for a Non-Null argument. Every vector whose error rests on a null, or a missing value, at a Non-Null argument, input field or list item cites §3.12 in its `spec`, whatever its check (134 vectors). |
| `variables` | §6.1.2 | MUST | Variable defaults (including null), missing and null values, a Non-Null variable, and a value that can't be coerced as a request error, even for an unused variable |
| `arguments` | §6.4.1 | MUST | Argument defaults, a missing variable falling back to the default, an explicit null not replaced by the default, a null variable for a Non-Null argument, and a literal that can't be coerced |
| `argumentErrorKind` | §6.4.1 | SHOULD | A coercion failure in CoerceArgumentValues is a field error, not a request error: "Any _request error_ raised as a result of input coercion during {CoerceArgumentValues()} should be treated instead as an _execution error_", while §3.5 and §3.12 call the failure a request error that "must be raised". September 2025 has the same sentence. October 2021's CoerceArgumentValues says "raise a field error" with no such sentence, and its §3.5 and §3.12 still say a request error; the kit takes the weaker reading there too. Where §3.10 or §3.10.1 itself requires the execution error (`executionErrorRequired`), a request error fails the vector's own check instead. |
| `getOperation` | §6.1 | MUST | The operation `operationName` names, or the only operation when there is no name; otherwise a request error. A mutation runs its mutation field, and only the selected operation's variables are coerced. Names are case-sensitive (§2.1.8): `a` and `A`, `getValue` and `getvalue` are different operations. |
| `descriptionsInert` | §2.2 | MUST | "Descriptions in GraphQL executable documents ... MUST NOT affect the execution, validation, or response of a GraphQL document. It is safe to remove all descriptions and comments from executable documents without changing their behavior or results." Each vector is the twin of the same request without its descriptions or comments, and rests on it (`restsOn`). Descriptions on operations and variable definitions are new in September 2025 (`since`, `newInput`); comments are in every edition. |
| `syntacticOrder` | §2.7, §2.10.8 | MUST | "Arguments may be provided in any syntactic order and maintain identical semantic meaning", and the same for input object fields. Each vector is the twin of the same request in the written order, and rests on it. One sends a variable's JSON map with its keys in another order. |
| `notExecutable` | §2.3 | MUST | "A Document which contains TypeSystemDefinitionOrExtension must not be executed": a request error, even where the document also holds an operation that would run. Graded for every adapter, validating or not. |
| `syntaxError` | §7.1.6, §6.1 | MUST | A document that doesn't parse is a request error: "a request error may occur due to a parse grammar or validation error in the Document", and "If a request error is raised, the response must be a request error result". `Parser.tla` says which documents don't parse, and graphql-js agrees. Graded for every adapter; no validator is asked. |
| `argumentsBelowRoot` | §6.4.4, §6.4.1, §7.1.4 | MUST | With `nested-fields`: an argument error on a field inside an object, a list, a Non-Null object or list, with aliases. The execution error nulls the field's position and propagates to the nearest nullable parent, one error per position (each list item is one), at the field's response path with indices and aliases. A value is one call per position with the coerced arguments. |
| `sourceStream` | §6.2.3.1 | MUST | With `subscription-source`: the source stream's resolver gets the subscription root field's coerced arguments, exactly once, by the field's name even under an alias, and the first event's result holds the field under its response name. |
| `sourceStreamError` | §7.1.6, §6.2.3.1 | MUST | With `subscription-source`, new in September 2026 (`since`): an error raised by the source stream's resolver is a request error. §7.1.5: "If an error was raised before operation execution begins, the response must be a request error result", and §7.1.6 now lists a "failure to establish a source event stream for a subscription operation". |
| `sourceStreamArguments` | §6.2.3.1, §6.4.1 | INFO | With `subscription-source`, since September 2026: a subscription root field's argument that can't be coerced. The text contradicts itself (see [Readings](#readings)), so a request error and an execution error both pass, and the report records which happened. A resolved value fails the type's own check (`typeCheck`: `nonNull` or `int`). |
| `unvalidatedBranches` | §6.3.2, §6.3.3, §6.2.3.1 | MUST | For adapters with `unvalidated`: a fragment spread whose fragment doesn't exist and a field the type doesn't define are skipped ("If no such fragment exists, continue", "If fieldType is defined"), and a subscription with two root fields, even one undefined, is a request error ("If collectedFieldsMap does not have exactly one entry, raise a request error"). For other adapters, these documents are invalid ones. |
| `invalidNotExecuted` | §6.1.1 | MUST | For adapters without `unvalidated` that claim `validate`: a document that Validation.tla rejects, and the implementation's own validator rejects too, fails as a request error, with no resolver called (see [Validation](#validation)). |
| `onlyValidExecuted` | §6.1.1, §5 | SHOULD | For adapters without `unvalidated`: a document that Validation.tla rejects, but whose errors the implementation's validator doesn't report (or the kit can't ask), isn't executed. "only operations from documents which pass all validation rules should be executed" |
| `acceptsValid` | §5 | MUST | For adapters without `unvalidated` that claim `validate`: a valid document isn't refused at validation. A request error on a valid vector whose document the implementation's validator rejects fails here, not under the vector's own check |
| `requestErrorNoData` | §7.1.3 | MUST | A request error has no `data` entry. September 2026 and September 2025: "The _request error result_ map must not contain an entry with key {"data"}." October 2021, §7.1: "If the request failed before execution, due to a syntax error, missing information, or validation error, this entry must not be present", and §7.1.2: "If a request error is raised, execution does not begin and the `data` entry in the response must not be present." Its §7.1.1 also has a "should not be present", but the two MUST sentences are the ones about request errors, so the check is a MUST in every edition. Every vector that accepts a request error exercises it. A vector that fails its own check doesn't also count here. |
| `responds` | §7 | MUST | A request gets a response, as in execution: "When a GraphQL service receives a _request_, it must return a well-formed response." No response always fails it, whatever the reference's answer: it says nothing about the coercion rule the vector is about. The finding names that rule as a hint ("on vectors of §3.10"), and groups by it. Every vector exercises it. |
| `fieldErrorPath` | §7.1.6, §7.1.4 | MUST | A field error's path is the field's response path. §7.1.6: an error associated with a field "must contain an entry with the key {"path"} with a _response path_ which describes the _response position_ which raised the error", and a response path names response positions (§7.1.4), not arguments. Every vector that accepts a field error exercises it. A field error the vector expects, but at another path, fails only this check. A field error the vector doesn't expect fails the vector's check, whatever its path. |
| `errorFormat` | §7.1.6 | MUST | Every error is a map with a string `message`, in every edition. Every vector exercises it |
| `additionalEntries` | §7.1.8 | MUST | No top-level entry other than `data`, `errors` and `extensions`, in every result, request errors included: "the _execution result_ and _request error result_ maps must not contain any entries other than those described above". October 2021, §7.1, says the same with "must". Execution's check of the same name. Every vector exercises it |
| `extensions` | §7.1.7 | MUST | A top-level `extensions` entry is a map: "The {"extensions"} entry in an _execution result_ or _request error result_, if set, must have a map as its value". October 2021, §7.1, says the same. Execution's check of the same name. Every vector exercises it |
| `resultMap` | §7.1.1, §7.1.3 | MUST | The response is a map: "An execution result must be a map", "A request error result must be a map". A `response` that is a list, a string, a number, a boolean or null fails here, rather than being taken as an adapter outside the result format. Every vector exercises it |
| `errorsList` | §7.1.1 | MUST | `errors`, when present, is a non-empty list: execution's check of the same name. September 2026 and September 2025: "If the request completed without raising any errors, this entry must not be present." October 2021, §7.1, says the same with "must"; its §7.1.2 also has a "should not be present", but the §7.1 MUST is the sentence about the entry, so the check is a MUST in every edition, as in execution. | `loneSurrogates` | none | INFO | A JSON string with a lone surrogate, for String or ID: kept as sent, replaced with U+FFFD, or refused with a request error. All three pass, and the report records which happened. It never fails the run (see [Lone surrogates](#lone-surrogates)). |
| `jsonNumbers` | none | INFO | For adapters without `exact-numbers`: a big JSON number may be read exactly, read as the nearest double, or refused with a request error (RFC 8259 §6). It never fails the run. |
| `requestExtensions` | §6.1 | INFO | With `request-extensions`: a request's `extensions` with keys under a prefix no service uses, each the twin of the same request without them. §6: "extensions (optional): A map reserved for implementation-specific additional information", "there are no additional restrictions on its contents". The spec gives the entries no meaning, and doesn't require a service to ignore them, so the check records whether the answer stayed the same and never fails the run. It cites §6.1 because `kit/spec-sections.json` has no entry for §6 itself. |

Findings group failures by kind and check:
- accepts what §X rejects;
- rejects what §X accepts;
- coerces to the wrong value under §X;
- runs a different operation than §6.1 selects;
- raises a field error where §6.1.2 requires a request error, or a request error where §6.4.1 says a coercion failure should be treated as a field error (`argumentErrorKind`), or where §3.10 or §3.10.1 requires one;
- leaves a SHOULD undone (`inputFieldDefaults`);
- gives October 2021's answer where September 2025 changed it (a vector with `since`, counted against its check);
- follows October 2021's §3.11 table of examples, which its prose contradicts (counted against `list`, in every edition);
- rejects a valid document at validation (`acceptsValid`);
- answers with an error that isn't a map with a string message (`errorFormat`);
- answers a value with an empty `errors` list (`errorsList`);
- answers a request error with a `data` entry (`requestErrorNoData`);
- answers with another top-level entry (`additionalEntries`), or an `extensions` that isn't a map (`extensions`);
- produces no response, though §7 says every request gets one (`responds`), one finding per check of the vectors it happened on. It has `"kind": "crash"` and the adapter's message as `problem`, and the summary counts crashes apart;
- raises the field error with a path other than the field's response path (`fieldErrorPath`);
- answers with a response that isn't a map (`resultMap`);
- answers a document that doesn't parse with something other than a request error (`syntaxError`);
- creates a subscription's source stream with other arguments than the field's, or not exactly once (`sourceStream`);
- treats a lone surrogate in a way nothing explains (`loneSurrogates`);
- executes a document its own validator rejects (`invalidNotExecuted`), or an invalid document its validator doesn't reject (`onlyValidExecuted`);
- reads a big JSON number in a way nothing explains (`jsonNumbers`), or gives an inexact Float integer a value other than the refusal or the nearest double (`floatPrecision`);
- answers with none of the three outcomes: a request error, a field error or a value.

The run fails on any failing MUST check, a failing SHOULD check with `--strict`, a result not in the format above, or a failed self-test.

**Self-test.** Every run also judges results built on purpose, in the same capabilities, through the same classification and comparison. Every answer a vector accepts must pass, and so must the expected answer with its null entries dropped, without `absent-vs-null`. Each of these wrong results must be caught:
- every verdict flipped (a value, a field error, a request error), where the spec doesn't permit the flipped answer;
- the answer to the nearest vector whose answer isn't accepted;
- an answer that leaves a SHOULD undone, which must count against that SHOULD's check;
- an answer that leaves out one input field default but keeps another, which must count against `inputFieldDefaults`, and the same answer with the kept default wrong, which must count against the vector's check;
- October 2021's answer to a vector with `since`, and the answer of October 2021's §3.11 table, which must each count against the vector's check;
- a crash on a vector with `since`, which must count under that release only where October 2021 can't take the input (a OneOf schema, a code point above U+FFFF, a description on an operation or variable definition), and a wrong answer to it, which always must;
- a request error on a valid vector whose document the validator rejects, which must count against `acceptsValid` (for adapters that validate), while the reference's own request error, which the validator doesn't explain, must pass;
- an undeclared null argument, and an undeclared null input field;
- a request error with `"data": null`, which must count against `requestErrorNoData`, or a request error after a resolver ran;
- a request error or field error whose error is `null`, has no `message`, or a `message` that isn't a string, each of which must count against `errorFormat`;
- a value with `"errors": []`, which must count against `errorsList`;
- no response, which must count against `responds`;
- a result with another top-level entry, which must count against `additionalEntries`, and one whose `extensions` is a list, which must count against `extensions`, while a map `extensions` must pass;
- a request error where the vector expects a field error, which must count against `argumentErrorKind`, or the vector's own check where §3.10 or §3.10.1 requires the execution error;
- a field error without a path, at the argument's path `["v"]`, or at a path inside the field, each of which must count against `fieldErrorPath`, or a field error after the resolver ran;
- a field error at the argument's path where the vector doesn't accept a field error, which must not count against `fieldErrorPath`;
- a value with an error, from two resolver calls, or from a call at another field;
- a response that is a list, a string or null, each of which must count against `resultMap`;
- for a vector below the root: a field error at only one of a list's positions, the same position's error twice (`fieldErrorPath`), a field error that nulls the whole data, or that nulls the field where the reference's null is at a parent, and a value whose positions got different arguments;
- for a subscription value: a source stream created with other arguments, not created, or created twice, each of which must count against `sourceStream`;
- a list or input object vector failing the way a vector it rests on fails, which must count where the inner one does, and the same vector failing while the inner one passes, or fails another way, which must stay with its own check.

## Vectors

[`kit/coerce/vectors.json`](../../kit/coerce/vectors.json) holds the schema, the other vectors' schemas (`schemas.oneOf`, `schemas.nested`, `schemas.subscription`), the declarations of every argument and input field (`inputs`), and 2219 vectors. [`scripts/generate-vectors-coerce.mjs`](../../scripts/generate-vectors-coerce.mjs) writes it. `--check` regenerates it and fails if it differs. graphql-js only parses the SDL and documents there, and finds the string literals in them. The generator also checks that `Parser.tla` and graphql-js agree on which documents don't parse, and that `Lexer.tla` and graphql-js read the lexing vectors' tokens the same way. Every answer comes from the references:

- **`expected`:** `Coercion!ExecuteSource` (ExecuteRequest on a document that parses and has no type system definition, else a request error) under the reference's default policy, which follows every SHOULD and takes JSON strings as enum values. `field` is the field `Coercion!GetOperation`'s operation selects, at the root or below it. A string literal's text, wherever one appears, is `Lexer!StringValueAt`'s.
- **`alternatives`:** the other answers the spec permits, from `ExecuteRequest` under the other policies. `policy` names the switches each needs: `enumFromString` (a MAY, so the answer passes), `inputFieldDefaults` (a SHOULD, so the answer fails `inputFieldDefaults`, as does one that leaves out only some of those defaults), or `missingListItemError`, `missingListItemDropped`, `floatRounded`, `variableItemWrapped` and `sourceArgumentsFieldError` (readings of what the spec doesn't say, so the answer passes; see [Readings](#readings)). `oct2021` is October 2021's answer to a vector with `since`: it fails the vector's check, but under its own finding. `oct2021Example` is the answer October 2021's §3.11 table of examples gives (see [Editions](#editions)), and with `validating` the request error a service whose validator follows the table too gives (only graded for adapters without `unvalidated`): they fail the vector's check, under their own finding.
- **`since`** and **`editionNote`:** the first release whose text gives the vector's answer (`"September2025"` or `"September2026"`), where an earlier release's text gives another answer, has no OneOf input objects, or can't read the document; and why (see [Editions](#editions)).
- **`newInput`:** October 2021 can't read the document (a description on an operation or variable definition), so a crash counts under `since`.
- **`schema`:** `"oneOf"`, `"nested"` or `"subscription"`, for vectors on `schemas.oneOf`, `schemas.nested` or `schemas.subscription`.
- **`unparsable`:** the document doesn't parse (`Parser!ParseExecutable` fails); graded under `syntaxError` for every adapter.
- **`subscribe`** and **`sourceCalled`:** what the source stream resolver does, and whether the reference calls it.
- **`typeCheck`:** for `sourceStreamArguments`, the check a resolved value fails.
- **`at`:** for the vectors below the root and the subscription vectors, the field, its response positions and the data with and without its error (see [Result](#result)), from `Coercion!Positions` and `Coercion!DataOf`.
- **`extensions`:** the request's extensions, as JSON text.
- **`restsOn`:** the vectors that hold this one's list items or input object fields on their own (see [Attribution](#attribution)). 550 vectors have one or more.
- **`binary64`:** the answer when the variables are read as a binary64 JSON parser reads them, where that differs from `expected`.
- **`loneSurrogate`:** `kept` and `replaced`, the answers when a JSON string's lone surrogate is kept as sent or replaced with U+FFFD, where they differ from `expected`. Such a vector's check is `loneSurrogates`.
- **`valid`:** `Validation!IsValid` for the document, and Coercion's scalar coercion for every Int and Float literal. §5.6.1 asks for literals to be "coercible", but `Validation.tla` checks literals by kind only.
- **`literalOnly`:** the 26 documents that are invalid only because a literal doesn't coerce, such as `{ int(v: 2147483648) }` and `{ float(v: 1e400) }`. For an adapter without `unvalidated`, they aren't graded under `invalidNotExecuted`: a request error passes as well as the reference's answer, and a resolved value fails the vector's check (see [Validation](#validation)).
- **`requires`:** `absent-vs-null` for vectors on the same field whose arguments differ only in a null entry versus an absent one, such as `{ int }` versus `{ int(v: null) }`; `nested-fields`, `subscription-source` and `request-extensions` for the vectors that need them, which aren't sent to an adapter without them, valid or not.
- **`executionErrorRequired`:** the 4 vectors where §3.10 or §3.10.1 itself says "an _execution error_ must be raised", so a request error fails the vector's check rather than `argumentErrorKind`.
- **`idFromInteger`:** the ID argument comes from an integer, so its format is the service's.
- **`check`, `spec`:** the check and sections the vector belongs to. `spec` adds §6.1.2 or §6.4.1 for the algorithm that raises the expected error, and §3.12 where the error rests on a null or missing value at a Non-Null position.

### Readings

A list item can be a variable: `query($x: Int) { ints(v: [1, $x]) }`. When the request gives `$x` no value and it has no default, §3.11 and §6.4.1 don't say what the item coerces to. §3.10 does say what happens for an input object field in the same spot: no runtime value and no default means no entry. A list has no entries to leave out. `Coercion.tla` reads the item as null by default, as graphql-js does, which is also what §5.8.5 implies by letting a nullable variable into a nullable item position. Its `missingListItem` switch gives the other two readings: the item can't be coerced (a field error), or the item is left out, by analogy with §3.10. All three are defensible from the text, so all three pass. Four vectors have such an item:

| Vector | Request | Expected | Also passes |
| --- | --- | --- | --- |
| `coerce-1940` | `query($x: Int) { ints(v: [1, $x]) }` with `{}` | `[1, null]` | a field error; `[1]` |
| `coerce-1943` | `query($x: Int) { intsNN(v: [1, $x]) }` with `{}` (invalid by §5.8.5) | a field error | `[1]` |
| `coerce-1951` | `query($x: Int) { matrix(v: [$x, [$x]]) }` with `{}` | `[null, [null]]` | a field error; `[[]]` |
| `coerce-1973` | `query($p: Point) { points(v: [$p]) }` with `{}` (invalid by §5.8.5) | a field error | `[]` |

A list item can also be a variable whose type doesn't fit the item type: `query($x: Int) { matrix(v: [$x, [$x]]) }`, where the first item's type is `[Int]`. §5.8.5 makes such a document invalid, so only adapters with `unvalidated` see the answer. §6.4.1's Note says "Variable values are not coerced because they are expected to be coerced by {CoerceVariableValues()} before _operation execution_ begins, and valid operations must only allow usage of variables of appropriate types", and §3.10 says an input object field's variable's "runtime value ... must be used", so `Coercion.tla` uses the value as it is by default, as graphql-js does: `[2, [2]]` for `{"x": 2}`. But the Note's premise, a valid operation, doesn't hold, and §3.11 says a value that is "_not_ a list" passed to a list type becomes "a list of size one", which would give `[[2], [2]]`. The text doesn't settle it, so the `variableItemWrapped` switch gives that reading too, and both pass. It changes only `coerce-1953`: with `{}` and `{"x": null}` (`coerce-1951`, `coerce-1952`) there is no value to wrap, and in a valid document such a variable has a list type, whose value is a list or null.

§3.5.2 says a Float input value "not representable by finite IEEE 754 (e.g. {NaN}, {Infinity}, or a value outside the available precision)" must raise a request error, without defining "outside the available precision". It can't mean every value without an exact double: `0.1` has none, and every implementation rounds it. `Coercion.tla` reads it, by default, as an integer input value a double can't hold exactly, so `99999999999999999999` and 2^53 + 1 are refused; a float input value, even an integral one such as the literal `1e23`, is rounded. Its `floatRounded` switch rounds integers too. Both readings pass, under the informational `floatPrecision` (`coerce-0424`, the literal, and `coerce-0473`, the JSON value for an adapter with `exact-numbers`).

A subscription root field's argument that can't be coerced, such as `subscription { eventNN(v: null) }`, has two answers in the text. CreateSourceEventStream calls CoerceArgumentValues, which says "raise an _execution error_", and §6.4.1 says "Any _request error_ raised as a result of input coercion during {CoerceArgumentValues()} should be treated instead as an _execution error_". But September 2026's ExecuteRequest calls CreateSourceEventStream before Subscribe, before operation execution begins (§6.2), and §7.1.5 says "If an error was raised before operation execution begins, the response must be a request error result"; §6.2.3.1's Note says "an error raised here will be a request error". `Coercion.tla` gives the request error by default and the execution error under its `sourceArgumentsFieldError` switch. Both pass under the informational `sourceStreamArguments`, and the report records which happened. 5 vectors have such an argument.

### Editions

The kit grades September 2026, the latest release. Most rules a coerce vector relies on that October 2021 doesn't have came in September 2025, and the parts of §3, §6 and §7 the input coercion checks grade read the same in September 2025 and September 2026 (the changes between them there are editorial, such as "operation execution" for "execution"). Two things the subscription vectors test are new in September 2026: an error establishing the source stream is a request error (`sourceStreamError`), and so, by default, is a source stream argument that can't be coerced (`sourceStreamArguments`). Those 9 vectors have `"since": "September2026"`: September 2025 runs CreateSourceEventStream inside Subscribe, and its §7.1.6 doesn't name the failure. Descriptions on operations and variable definitions are new in September 2025 (`newInput`: October 2021 can't read those 9 documents, so a crash counts under `since`).

September 2025 and later coerce default values. Their CoerceVariableValues and CoerceArgumentValues say "Let {coercedDefaultValue} be the result of coercing {defaultValue} according to the input coercion rules", and their §3.10 uses "the result of coercing the default value" of an input field. October 2021 says "Add an entry to {coercedValues} named {variableName} with the value {defaultValue}" (and the same for arguments), and that an input field's "default value should be used". So under October 2021 `[Int] = 1` gives `1`, not `[1]`, and `ID = 9` gives `9`, not `"9"`. An implementation that coerces defaults anyway gets September 2025's answer.

Every edition's §3.11 also coerces a list item that isn't a list, where the item type is a list, as a list of one: "list values are accepted only when each item in the list can be accepted by the list's item type", and a value that is "_not_ a list and not the {null} value" is accepted as "a list of size one ... (note this may apply recursively for nested lists)". That prose is the same in every edition. Only the tables of examples disagree on `[1, 2, 3]` for `[[Int]]`: September 2025's and September 2026's give `[[1], [2], [3]]`, October 2021's "Error: Incorrect item value". Examples are non-normative in every edition ("Examples in this document are non-normative", October 2021's conformance section), so the 11 vectors with such an item carry no `since`. October 2021's table answer is recorded as an `oct2021Example` alternative, so that a result following it is named: it fails `list`, under its own finding, "follows October 2021's §3.11 table of examples". For the 5 literal vectors (`{ matrix(v: [1]) }` and the like), a service that follows the table in its validator too refuses the document as not "coercible" (§5.6.1), a request error. That answer is recorded as well (`validating`), and graded only for adapters without `unvalidated`. An implementation whose validator accepts the document and whose executor follows the table gives a field error, which also counts as following the table.

`Coercion.tla` follows September 2026. Its `coerceDefaults` switch gives October 2021's answer for defaults, which uses each default as written, and its `nestedListItems` switch gives the answer of October 2021's table. The generator evaluates every vector under the default policy, under each switch, and under both. The 25 vectors whose answers differ under `coerceDefaults` have `"since": "September2025"`. `editionNote` says why and gives October 2021's answer, which is also an `oct2021` alternative unless another alternative already gives it. They are `[Int] = 1`, `[[Int]] = 1`, `ID = 9`, `Point` defaults that leave out `y` (which has its own default, 0), and `Shape`'s `tags: [String!] = "shape"`. Enum and `Float = 2` defaults give the same answer either way. The 20 OneOf vectors have it too: October 2021 has no `@oneOf` (September 2025's §3.10.1 and §3.13.5 add it), so their schema isn't valid there. So does `{ string(v: "é😀") }`: October 2021's SourceCharacter is U+0009, U+000A, U+000D and U+0020–U+FFFF, and read literally, as the [parse area](parse.md) reads it, a raw U+1F600 isn't one; September 2025's is any Unicode scalar value. The validate area tags its own vectors; that is its own page's business.

Vectors with `since` are graded like any other. A result that gives October 2021's answer fails the vector's check under its own finding, "gives October 2021's answer where September 2025 changed it". Where October 2021's answer is also an answer without input field defaults (a `Point` default under October 2021 has no `y`), it fails `inputFieldDefaults` instead. A finding's `since` counts its vectors that rely on a rule new in each release (`{"September2025": 3}`; left out where there are none), and its example starts with `[since September 2025]` when it is one of them. The report's `since` gives, per release, how many such vectors were run and how many failed (`{"September2025": {"vectors": 46, "failing": 3}}`), and each check's `failingSince` how many of its failing vectors rely on a rule new in each release, so a sheet can show a check whose failures are all such vectors. A crash counts there only where October 2021 can't take the input at all, the OneOf vectors, the raw U+1F600 and the descriptions (`newInput`): on a default value vector or a source stream vector, it fails in every edition, as [the contract](../kit-areas.md) says.

### Lone surrogates

JSON can escape a lone surrogate: `{"x": "\ud800"}`. Two vectors send one, to String (`coerce-0584`) and to ID (`coerce-0786`). §3.5.3 accepts "only valid Unicode string input values" but never defines one, and calls a String "a sequence of Unicode code points", which a lone surrogate is. §3.5.5 says nothing about Unicode. What a JSON parser does with the escape varies, and RFC 8259 §8.2 calls it unpredictable: it may keep it, replace it with U+FFFD, or refuse the text. `Coercion.tla` refuses it, as a request error.

So the kit doesn't grade these two vectors under `string` or `id`. They count toward the informational `loneSurrogates` check, which passes a request error, the value kept as sent, and the value with U+FFFD, all three from `Coercion.tla`. The check's `observed` in the report counts which happened, and its `note` says it in words. The kit marks them informational, not unspecified, because what an implementation does is still worth recording. An adapter whose JSON parser refuses the variables outright answers `unsupported` instead of making up a request error (see [Result](#result)): then neither these two nor the 17 other vectors with a lone surrogate in their variables are graded, since the implementation never saw them.

### Big numbers

The JSON values include `9007199254740993` (2^53 + 1) and `1e400`. The reference reads JSON numbers exactly:
- a Float variable of 2^53 + 1 is a request error, since a double can't hold it;
- an ID variable of 2^53 + 1 is the string `"9007199254740993"`;
- an ID variable of 1e400 is a 401-digit string.

JSON lets a parser limit range and precision (RFC 8259 §6). `JSON.parse` rounds 2^53 + 1 to 2^53, and turns 1e400 into Infinity, before coercion starts. Accepting the Float 2^53 is then correct coercion. So for an adapter without `exact-numbers`, these 3 vectors count only toward `jsonNumbers`, which passes on the exact answer, the `binary64` answer, or a request error. With `exact-numbers`, they count toward `floatPrecision` (informational: refused and rounded both pass) and `idCoerced` against the exact answer.

## graphql-js

[`adapters/graphql-js/areas/coerce.mjs`](../../adapters/graphql-js/areas/coerce.mjs) sends the result of `execute` and its resolver calls, and supports `absent-vs-null`. It runs two ways:

- **By default**, it runs `execute` without `validate`, and claims `unvalidated`.

It also claims `nested-fields`, `subscription-source` (a subscription operation goes through `subscribe` with a `subscribeFieldResolver`) and `request-extensions` (graphql-js's `execute` takes no request extensions, so the adapter parses them and drops them), and answers a syntax error from `parse` as a request error.
- **With `--validate`** (`node adapters/graphql-js/adapter.mjs --graphql 17 --validate`), it validates first and doesn't claim `unvalidated`, so the kit grades the invalid documents under `invalidNotExecuted`, asking graphql-js's validator through the validate area. Both versions pass all 785. The validator accepts the literal `1e400`, which then reaches the resolver as Infinity, so `float` fails as it does without validation.

Unvalidated, both versions fail these checks:

- **§3.5.2 Float (MUST):** the literal `1e400` is accepted as Infinity.
- **§2.3 Document (MUST):** `execute` skips type system definitions, so 5 of the 6 `not-executable` documents run their operation. The sixth has no operation, a request error. With `--validate`, the Executable Definitions rule refuses all 6.
- **§6.3.2 and §6.2.3.1 (`unvalidatedBranches`, MUST):** a subscription with two root fields is executed for its first field's source stream instead of refused, `subscription { event(v: 1) nope }` resolves `event`, and `subscription { event(v: 1) eventNN(v: 1) }` resolves both. graphql-js leaves that rule to validation (Single Root Field).

The literal `99999999999999999999` is rounded to 1e20, which `floatPrecision` records (informational).
- **§3.10 Input Objects (MUST), 16 only:** an unknown field in an input object literal is ignored. That happens in 5 vectors, one of them `{ points(v: { x: 1, z: 1 }) }`, which rests on `{ pointNN(v: { x: 1, z: 1 }) }` and so counts under §3.10, not §3.11. 17 rejects it.
- **§3.10.1 OneOf (MUST, since September 2025), 16 only:** a OneOf literal with a variable entry that has no runtime value, `{ a: "abc", b: $b }` with `$b` missing, counts as one entry (2 vectors). 17 refuses it. Both documents are invalid, so only `execute` without `validate` sees them.

Both pass every other new check, validating or not: descriptions and comments, syntactic order, case-sensitive operation names, the 16 documents that don't parse, argument errors below the root, the source stream's arguments, and a source stream that raises (a request error, as September 2026 says). Both give a request error for a source stream argument that can't be coerced, and the same answer with and without request extensions.

Both keep a lone surrogate as sent, which `loneSurrogates` records. The big JSON numbers pass `jsonNumbers`, and the ID `1e21` passes as `"1e+21"`, though `differential-coercion.mjs` still lists these three in `KNOWN`, next to the disagreements above, since it compares with the reference's exact answer.

## Limits

- **OneOf:** only §3.10.1's input coercion, on one OneOf input object with two scalar members. An implementation that can't build a schema with `@oneOf` crashes on the 20 OneOf vectors, whose `since` is September 2025.
- **String values:** only escapes and block strings that read the same in every edition. Braced escapes (`\u{...}`) and surrogate pair escapes are left out, as is any JSON string decoding, which is the JSON parser's.
- **Editions:** only default values, OneOf input objects, a raw supplementary character and list items are compared with October 2021 (see [Editions](#editions)). The main schema uses nothing newer than October 2021. No release has its own profile: a result that follows September 2025 is graded against September 2026, which gives the same answers here.
- **Fractional floats:** the reference keeps a fractional Float as its decimal rather than rounding it to a double. That is exact for decimals of at most 15 significant digits, and the vectors only use those.
- **Fixed schema:** one schema and its OneOf, nested and subscription variants, no custom scalars, and no directives other than `@oneOf`. Root field names are unique across Query, Mutation and Subscription, so the field a resolver ran at says which root type ran. Below the root, only one path of fields is selected per vector, and a list of objects always has two items.
- **Descriptions:** only on operations and variable definitions, and comments anywhere. The encoding has no fragment spread that runs, so a description on a fragment definition isn't sent here.
- **Subscriptions:** only the source stream's creation and the first event's result. What a later event does, and how the stream ends, is execution's (`subscription-stream`).
- **Request extensions:** only keys no service gives a meaning to, and the check is informational. Whether `extensions` must be a map isn't graded: the kit always sends one.
- **Result coercion** (§3, output values): not this area's. Its resolvers return fixed values; execution grades result coercion.
- **What isn't compared:** error messages and locations, how many errors a request error has, and whether a request error's errors carry a path (no sentence says they mustn't).
- **Validity:** a vector's `valid` flag comes from `Validation.tla`, and Validation's own limits apply. For an adapter that validates and claims `validate`, a validator stricter than `Validation.tla` shows up under `acceptsValid`. Without `validate`, it shows up as a failure of the vector's own check. The kit takes the validate area's verdict to be the one the implementation's request pipeline uses.
- **Lone surrogates:** only recorded, never graded (see [Lone surrogates](#lone-surrogates)).

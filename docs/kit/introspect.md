# The introspect area

`graphql-tla run introspect` checks schema introspection: what an implementation answers to the standard introspection query, and to `__type(name:)`, for an SDL schema. The reference is [`specs/Introspection.tla`](../../specs/Introspection.tla). `SchemaResult` is the `__schema` a service must return, and `Matches` says whether a service's result is one the spec allows. `TypeByName` is the answer to `__type(name:)`, and `TypeByNameMatches` judges one. It covers:

- §4.1 `__typename`;
- §4.2 Schema Introspection: `__schema` and `__type(name:)`, and `__Schema`, `__Type` for each kind (List and Non-Null included), `__Field`, `__InputValue`, `__EnumValue` and `__Directive`, as in September 2026, the latest release, including `isOneOf`, `specifiedByURL` and deprecated arguments, input fields and directives;
- the same against September 2025 or October 2021, for an implementation whose introspection types are an older release's, or lack some of a release's fields or arguments (see [Profiles](#profiles));
- §3.5's rule on which built-in scalars appear, and when §3.13 says a service must or should provide each built-in directive, including `@skip` and `@include` once a request shows the service honours them;
- §2.10.4's rule on producing a StringValue, for the strings in a printed default value (since September 2025), and §2.10.4's string and block string values in descriptions;
- the response envelope of §7.1.1, §7.1.7 and §7.1.8.

```shell
npx graphql-tla run introspect --adapter "node adapters/graphql-js/adapter.mjs --graphql 17" --strict --report introspect.json
```

The area follows [the contract for areas beyond execution](../kit-areas.md).

## Request

```json
{"type":"introspect","id":12,"sdl":"type Query { a: Int }","query":"query IntrospectionQuery { __typename __schema { … } } …"}
```

- **`sdl`:** a valid type system document, with no extensions.
- **`query`:** one of the kit's queries, in [`kit/introspect/query.mjs`](../../kit/introspect/query.mjs). The introspection query is the usual full query (graphql-js's `getIntrospectionQuery` with every option on), with every field of the profile's introspection types, plus `__typename` at the root. Each schema is asked the query twice: once with `includeDeprecated: true` on every list that takes it, once without the argument. A lookup query asks `__type(name:)` for a few names, each under an alias (`t0: __type(name: "Query") { ...FullType }`), with the same `FullType` fragment. One more request, the `wrappers` vector, asks `wrappers: __type(name: "__Schema") { fields { name type { … } } }`, with every `__Type` field selected three levels down, so that the List and Non-Null types of `__Schema`'s fields show their other fields. It is sent on its own, so that a service that rejects it (Hot Chocolate does, without a raised list depth limit) still has everything else graded. `wrappers.user` asks the same of a type the document defines (`__type(name: "Resource")`, four levels down).

A few vectors send other requests:

- **`roots.lookup.fragments`** is a lookup whose `__type(name:)` fields sit in an inline fragment (`... on Q { … }`) and a named fragment (`fragment Lookups on Q`) on the query root, not directly in its selection set (§4.2: the meta-fields "are implicit" on the query root, and fragments on it are part of it).
- **`probe.skip` and `probe.include`** send `{ __typename kept: __typename @skip(if: false) dropped: __typename @skip(if: true) __schema { directives { name } } }` (and the same with `@include`, true and false swapped).
- **`emptySelection.root` and `emptySelection.meta`** send `{}` and `{ __typename __schema {} t0: __type(name: "Query") {} t1: __type(name: "Unknown") {} }`. Empty selection sets are new in September 2026 (§2.5), so these have only September 2026's query.

Build the schema from the SDL, with no resolvers needed, and execute the query against it.

## Result

```json
{"type":"result","id":12,"response":{"data":{"__typename":"Query","__schema":{…}}}}
```

- **`response`:** the execution result, as JSON, exactly as the implementation would send it. If the schema doesn't build or the query is rejected, answer with a request error: `errors` and no `data` entry. That is an answer, and fails the `executes` check (or `builtinDirectives`, for a schema in `needs`, and nothing, for a schema in syntax only September 2026 has: see below). `{"data": null, "errors": [...]}` is an execution failure, not a request error (§7.1.7: a request error "must not contain an entry with key `data`"), and always fails `executes`. For the probe that picks the profile, though, either one counts as the query being rejected.

If the implementation crashes (it throws on building the schema, or while executing, instead of answering), answer `{"type":"error","id":12,"message":"…"}`, as in the other areas: the kit records a crash for that vector, which fails `executes`, and goes on ([crashes](../kit-areas.md)). Don't turn a crash into a request error: that hides it.

**`custom-directives`.** Schemas that declare a directive of their own (`directive @label(...) on ...`: `rich`, `builtinScalars`, `directiveDeprecation`, `directiveArgDeprecation`, `locations` and `directiveDefinitionLocation`) carry `"requires": ["custom-directives"]`. An adapter claims the capability when it builds such a schema from SDL and the implementation knows the directive. Without it, those vectors aren't asked, and the report's `provenance.skipped` counts them.

The area needs SDL input. A code-first framework that can't build a schema from SDL can't take part. It just doesn't claim the `introspect` capability.

## Profiles

Each release has its own introspection types and built-in directives (§4.2, §3.13, Appendix D). What October 2021 has, and what each later release adds or changes:

| | October 2021 | September 2025 | September 2026 |
| --- | --- | --- | --- |
| `__Type` | `fields` and `enumValues` take `includeDeprecated: Boolean = false` | `isOneOf`; `includeDeprecated: Boolean! = false` on `fields`, `enumValues` and `inputFields` | |
| `__Field`, `__Directive` | | `args(includeDeprecated: Boolean! = false)` | `__Directive.isDeprecated` and `deprecationReason` |
| `__InputValue` | | `isDeprecated` and `deprecationReason` | |
| `__Schema` | | | `directives(includeDeprecated: Boolean! = false)` |
| `__DirectiveLocation` | | | `DIRECTIVE_DEFINITION` |
| `@deprecated` | `(reason: String = "No longer supported") on FIELD_DEFINITION \| ENUM_VALUE` | `reason: String!`; `ARGUMENT_DEFINITION` and `INPUT_FIELD_DEFINITION` | `DIRECTIVE_DEFINITION` |
| `@oneOf` | | `directive @oneOf on INPUT_OBJECT` | |

September 2025's Appendix D still printed `includeDeprecated: Boolean = false` where its §4.2 has `Boolean! = false` (#1142; September 2026 corrected the appendix, #1192). The kit follows §4.2. A service without one of a release's fields or arguments rejects a query that asks for it. So the kit picks, per run, a profile (`"September2026"`, `"September2025"` or `"October2021"`), and the fields and arguments to leave out:

1. It sends the first vector (`minimal.inc`, `type Query { a: Int }`) with September 2026's query. Anything but a rejection keeps the **September 2026 profile**. A rejection is a request error (`errors` and no `data` entry), or errors with `"data": null`, which some services answer for a query they don't validate.
2. Otherwise it sends September 2025's query. Answered, that is the **September 2025 profile**.
3. Otherwise it asks which fields the introspection types have, and their arguments: `__type(name: "__Schema") { fields { name args { name } } }`, and the same for `__Type`, `__Field`, `__InputValue`, `__EnumValue` and `__Directive`, in one query. For September 2026 and September 2025, if every field and argument the release's query needs but the service lacks is one the kit can do without (below), it sends that query without them, the release that lacks fewer first (September 2026 on a tie). Answered, that is the release's profile without them.
4. Otherwise it sends October 2021's query. Answered, that is the **October 2021 profile**.
5. Otherwise, October 2021's query without what the service lacks, if the kit can do without it.
6. Otherwise the run stays with September 2026's profile, and every vector fails `executes`.

No capability is involved, and an implementation can't choose. One that answers September 2026's query is graded against September 2026; one whose introspection types are exactly September 2025's answers its query, and is graded against September 2025. The report records the choice in `profile`, the fields and arguments left out in `missingFields`, and `profileNote` says why, quoting the first error of each rejected query.

**Missing fields and arguments.** The kit can do without these:

| Field or argument | What the kit can't see without it |
| --- | --- |
| `__Schema.description`, and `description` on `__Type`, `__Field`, `__InputValue`, `__EnumValue` and `__Directive` | those descriptions |
| `__Type.specifiedByURL` | URLs |
| `__Type.isOneOf` | whether an input object is OneOf, and where `isOneOf` is null |
| `isDeprecated` and `deprecationReason` on `__Field`, `__InputValue`, `__EnumValue` and `__Directive` | which of those are deprecated |
| `__InputValue.defaultValue` | default values, and how they are printed |
| `__Directive.isRepeatable` | which directives are repeatable |
| `includeDeprecated` on `__Schema.directives`, `__Type.fields`, `enumValues` and `inputFields`, `__Field.args` and `__Directive.args` | whether that list returns deprecated items as `includeDeprecated: true` asks (the query leaves the argument out, so the list takes the service's default) |

Each vector is asked its profile's query without them. Before the comparison, a missing field's values are filled in with `null`, or `false` for `isDeprecated` and `isRepeatable`, and the missing definitions are put back into the introspection types the service returned (in `types`, in lookups and in `wrappers`), as the profile's built-ins define them. What the service lacks then counts **once per run**: one case of `builtinDefinitions` (MUST, §4.2 and §3.13: the introspection types "are fully defined" there), with one finding naming every missing field and argument. It rests on the release after the newest older edition that defines none of them: missing `__Directive.isDeprecated` under September 2026 is new in September 2026, missing `__Type.isOneOf` under September 2025 is since September 2025, and missing `__Type.specifiedByURL` rests on no release. In each result, the problems the kit can't see without a missing field or argument (the right-hand column) aren't counted, and everything else is graded as usual. Without any other field, such as `__Type.kind`, `__Field.type` or `ofType`, nothing can be graded.

Under an older release's profile:

- Each vector is asked `queries.September2025` or `queries.October2021`, that release's query.
- The built-in definitions are that release's (`Introspection!Sep2025Builtins`, `Oct2021Builtins`), as in the table above. An answer that matches them passes `builtinDefinitions`. Under October 2021, a `@oneOf` the service returns counts as a directive of its own.
- Vectors whose schema the release can't express aren't sent, and `provenance.skipped` counts them: under September 2025, those with `"since": "September2026"` (a deprecated directive or the location `DIRECTIVE_DEFINITION`, whose syntax is new in September 2026, and empty selection sets); under October 2021, every vector with `since` (also a OneOf input object, a deprecated argument, input field or directive argument, or a string only September 2025's lexical grammar has).
- Under October 2021, `isOneOf`, `order` and `defaultValuePrinting` are `untested`, with a note: October 2021 has no OneOf input objects, no Stable Ordering and no rule on producing a StringValue. `deprecation` is graded for fields and enum values only. October 2021 says "`deprecationReason` optionally provides a reason why this field is deprecated", where September 2025 and September 2026 say it "returns the reason". So under this profile a `null` reason for a deprecated field or enum value fails `deprecationReasonOmitted`, a SHOULD, and not `deprecation`. Another string still fails `deprecation`. Under the other profiles `deprecationReasonOmitted` is `untested`, with a note.
- The fields the release's query doesn't select are filled in before the comparison, with the only values a schema that release can express allows: under October 2021, `isOneOf` false for an input object and null otherwise, and no input value or directive deprecated; under September 2025, no directive deprecated. `IntrospectionVectors.tla`'s `Sep2025ProfileIsSound` and `Oct2021ProfileIsSound` check that `SchemaResult` gives exactly those values for such a schema.

**Releases of the built-ins.** Every answer with problems is also compared with each other release's built-ins. "The answer follows a release" at a problem means that comparison finds no problem at the same place, and none with the built-in list it belongs to, left out or added.

- A problem with a built-in definition, addition or Non-Null wrapping, where the answer follows a later release than the profile's, counts under `builtinEdition`, which is informational, and not under `builtinDefinitions`, `builtinAdditions` or `builtinNullability`: the answer is as that release defines it. It is labelled with the first later release it follows ("isn't as October 2021 defines it, but is as September 2025 does").
- Otherwise, the older releases are tried, newest first. If the answer follows one (O), or O doesn't define the field or argument at all (an addition never counts as undefined), the problem rests on the rule the release after O introduced: it is labelled `since` that release. Under September 2026, `@deprecated(reason: String = …)` follows October 2021, not September 2025, so it is since September 2025; `__Directive.isDeprecated: Boolean`, which September 2025 doesn't define, is new in September 2026. The finding says which ("it is as October 2021 defines it", "September 2025 doesn't define it").
- A problem no release explains rests on no release.

A built-in directive's `locations` are compared as two problems: locations left out, and locations added. Each is judged on its own. Under September 2026, a `@deprecated` with September 2025's four locations (`DIRECTIVE_DEFINITION` left out) follows September 2025: the failure is new in September 2026 ("lacks only locations September 2025 doesn't define"). With October 2021's two locations, it follows October 2021 and not September 2025: since September 2025. Under October 2021, a `@deprecated` with September 2025's four locations follows September 2025, and counts under `builtinEdition`, labelled September 2025. A location no release has, or one every release has left out, stays a `builtinDefinitions` failure, labelled with no release.

So an implementation whose introspection types and built-ins are exactly September 2025's gets the September 2025 profile and fails nothing; graded against September 2026 (the self-test does), its only failures are labelled new in September 2026.

## What is checked

First the kit checks the response's shape, in JS ([`kit/introspect/data.mjs`](../../kit/introspect/data.mjs)):

- **The envelope** (§7.1.1, §7.1.7, §7.1.8): the response is a map with `data`, or with `errors` and no data. `errors`, when present, is a non-empty list of maps with a `message`: `errors: []` and `errors: "not a list"` fail `envelope`. `extensions`, when present, is a map. No other entries. A bad envelope fails `envelope` only: the data is still graded.
- **The selected fields:** the data has exactly the fields the query selects, at every level, with an explicit `null` where a value is null. A missing field, such as an `ofType` the `TypeRef` fragment selects, or one the query doesn't select, fails `executes`, and nothing else is graded.

Then tla-ts evaluates `Introspection!Matches` (`TypeByNameMatches` for a lookup, `WrapperMatches` and `SchemaFieldsMatch` for `wrappers`) and [`kit/introspect/IntrospectChecks.tla`](../../kit/introspect/IntrospectChecks.tla)'s `Problems`. `Problems` compares with the reference's own operators, item by item, and names the aspect of each difference. `Matches` stays the verdict: the kit stops with an error if `Problems` finds a difference `Matches` doesn't, and counts a mismatch `Problems` can't name against `other`. `Matches` compares with the profile's definitions exactly. Where the text gives a difference a weaker level than MUST (a `null` default, URL or October 2021 reason, Non-Null on a built-in, a type nothing references, order, descriptions), `Problems` gives it an aspect of its own, and the kit grades it under a SHOULD or informational check.

The comparison allows what the spec allows:

- **`types`** is a set: any order.
- **`possibleTypes`** of an interface and a directive's **`locations`** have no source order: any order.
- **Built-in lists** have no source order either. The fields of `__Type`, the values of `__TypeKind`, and every other list of a built-in type or directive are compared by name, each once. The appendix's order isn't normative. Order is graded only where the document gives one.
- **`defaultValue`** is re-parsed, and two encodings match when they coerce to the same value for the input value's type: `1` and `[1]` for `[Int]`, `1` and `1.0` for `Float`.
- **Descriptions.** §3.2 says documentation is "made available via introspection", with no key word, and §4.2 says each `description` field "may return a String or null". So `descriptions` is a SHOULD: a description the document gives, the schema's included, should come back as it is. A definition the document doesn't describe may have any description: `null`, `""` or one of the service's own. Built-ins may have any description: the spec gives none.
- **Built-in directives** (§3.13): `Matches` compares the result with `SchemaResult` for the built-in directives the service provides: the ones it returns in `directives`, and the ones the result shows it provides (below). Each one must be as §3.13 defines it. Which ones it should provide depends on the schema, since every schema here comes from SDL:
  - `@deprecated` is a MUST "if representing deprecated portions of the schema": a schema that deprecates a field, argument, input field, enum value or directive. A missing `@deprecated` there fails `deprecation`. Elsewhere it may be left out.
  - `@skip` and `@include` are a SHOULD, for every schema.
  - `@specifiedBy` is a SHOULD "if representing custom scalar definitions": a schema with a custom scalar.
  - `@oneOf` is a SHOULD "if representing OneOf Input Objects": a schema with one. It is new in September 2025: the October 2021 edition has no OneOf input objects. A finding about it says "(since September 2025)".

  A missing SHOULD fails `builtinDirectives`. But "all provided directives, including any built-in directive, must be included in the set of returned directives" (§3.13), and `directives` "must return the set of all directives available within this schema including all built-in directives" (§4.2.1). So a directive the result shows the service provides is a MUST: a non-null `specifiedByURL` shows `@specifiedBy`, and a true `isOneOf` shows `@oneOf`. Leaving it out of `directives` fails `directives`, and only `directives`: the URL or the `isOneOf` is then graded against the document, as for a service that returns the directive. A wrong URL still fails `specifiedByURL`. For `__type(name:)`, the kit takes the built-in directives from the same schema's `__schema` answer, and adds those the lookup's own answer shows.

  A service that doesn't provide `@specifiedBy` or `@oneOf` can't represent them: every `specifiedByURL` is null, and every `isOneOf` false. Such a result breaks only the SHOULD. A vector whose schema applies `@specifiedBy` or `@oneOf` lists it in `needs`. If such a schema gets a request error while the profile's query is answered for other schemas (the first vector), the service doesn't provide the directive. That fails `builtinDirectives`, not `executes`.

  The reference states these conditions as `RequiredDirectiveNames`, `RecommendedDirectiveNames`, `ShownDirectiveNames` and `AsProvided`.
- **Other directives:** "GraphQL services and client tooling may provide any additional custom directive". A directive the service returns that is neither in the document nor one of §3.13's is accepted as the service describes it. So are the types its arguments reach, through input fields too, that the document doesn't define: they count as the schema's types, and as referencing the built-in scalars they use, for §3.5's rule. They must be input types, or the result fails `directives`. A type of the service's own that nothing in the schema reaches still fails `types`.
- **Default values** (§4.2.4): "defaultValue may return a String encoding (using the GraphQL language) of the default value used by this input value in the condition a value is not provided at runtime. If this input value has no default value, returns null." By Appendix A a lowercase "may" keeps its RFC 2119 meaning. So `null` for an input value that has a default, `n: Int = null` included, fails `defaultValueOmitted`, a SHOULD. A string that doesn't encode the default, or a string for an input value without one, fails `defaultValue`, a MUST.
- **Non-Null on built-in fields and arguments:** the Non-Null wrapping of the introspection fields and arguments, and of the built-in directives' arguments, comes only from the definitions: §4.2 introduces them with "Below are the full set of type system definitions … which are fully defined in the sections below", which has no key word, and §3.13.3 has `directive @deprecated(reason: String! = "No longer supported")`. The prose says what each field returns ("isRepeatable must return a Boolean") and, of `includeDeprecated`, only "Accepts the argument `includeDeprecated` which defaults to {false}". So the kit takes the weaker reading for both. A built-in field whose type differs from the spec's only in Non-Null (`isRepeatable: Boolean` for `Boolean!`) fails `builtinNullability`, a SHOULD: it can still return exactly what the prose says. So does a built-in argument that is nullable where the spec's is Non-Null, with nothing else in its type changed (`includeDeprecated: Boolean = false` for `Boolean! = false`, `@deprecated(reason: String = …)`): it accepts every value the spec's does. Its default is compared on its own, under `builtinDefinitions`. A built-in argument that is Non-Null where the spec's is nullable rejects requests the spec accepts, and fails `builtinDefinitions`. A field, argument or input field of the document's that differs only in Non-Null still fails `fields`, `arguments` or `inputFields`.
- **`specifiedByURL`** (§4.2.2): "`specifiedByURL` may return a String (in the form of a URL) for custom scalars, otherwise must be {null}". As for `defaultValue`, the lowercase "may" makes the URL optional. So `null` for a scalar the document gives a URL, from a service that provides `@specifiedBy`, fails `specifiedByURLOmitted`, a SHOULD. Another URL, or a URL on anything but a custom scalar that has one, fails `specifiedByURL` (or `typeKinds`, for a type that isn't a scalar), a MUST.
- **The reason of an item deprecated without one** is the default of `@deprecated(reason:)`. The reference fills in §3.13.3's `"No longer supported"`. If the service's own `@deprecated` (in its `__schema` answer, which a lookup takes from the same schema's) has another default, the kit judges the answer against the schema with that default written out wherever the document leaves the reason to it (`withReason` in `run.mjs`). The service's answer then agrees with the directive it describes, and the different default fails `builtinDefinitions` once, not `deprecation` again at every item deprecated without a reason. A reason the document writes out is still compared as it is.
- **Types nothing references** (§4.2.1): "`types` must return the set of all named types contained within this schema. Any named type which can be found through a field of any introspection type must be included in this set." The second sentence is about types found through fields. Whether a type the document defines but nothing reaches is "contained within this schema" the text doesn't settle. The reference expects it in `types`, and its lookup to find it. Leaving it out, or answering `null` for it, fails `unreferencedTypes`, a SHOULD, and not `types` or `typeByName`. "Reaches" means through the root operation types, the fields, arguments and input fields of the types reached, their interfaces, union members and an interface's implementations, and the directives' arguments (`IntrospectChecks!Referenced`).
- **Order** ("Stable Ordering", §4) is a SHOULD, since September 2025. A list with the right items in another order fails `order` only. That covers input fields, the document's directives and their arguments as well as fields, arguments and enum values. A directive's `locations` have no source order.
- **Printed default values** (§2.10.4, since September 2025): "When producing a StringValue, implementations should use escape sequences to represent non-printable control characters (U+0000 to U+001F and U+007F to U+009F)", and "If an implementation chooses to escape a supplementary character, it should only use a variable-width unicode escape sequence." The kit reads each string token in a `defaultValue` with `Lexer.tla`'s string grammar (`IntrospectChecks!PrintingProblems`). A string token with a raw control character, or a block string with one (a block string can't escape anything, so a line feed counts), or `\uD83D\uDE00`-style escapes of a supplementary character, fails `defaultValuePrinting`, a SHOULD. The value the string stands for is still graded by `defaultValue`. A raw supplementary character, or `\u{1F600}`, passes.
- **A request that uses `@skip` or `@include`** (the `probe` vectors): §3.13 says "all provided directives, including any built-in directive, must be included in the set of returned directives". If the service answers the request, with `kept` and without `dropped`, it provides the directive, and leaving it out of `__schema.directives` fails `directives`, a MUST. A request error fails `builtinDirectives`, the SHOULD the service then breaks. Data that isn't exactly `__typename`, `kept` and `__schema` fails `executes`. `Introspection!HonoredDirectivesMatch` states the rule.
- **Empty selection sets** (the `emptySelection` vectors, new in September 2026): the response must be exactly `{"data": {}}`, or `__typename`, `{}` for `__schema` and the found type, and `null` for the unknown one. Anything else fails `executes`. A request error isn't graded (`syntax`).

What the spec doesn't allow:

- **Built-in scalars:** "all referenced built-in scalars must be included", and an unreferenced one "must not be included". The introspection types reference `String` and `Boolean`, so those two always appear.
- **Introspection types:** `types` includes the eight introspection types, since "any named type which can be found through a field of any introspection type must be included". Each field, argument and enum value §4.2 defines must be there, as it defines it.
- **`__type(name:)`:** the named type's entry in `types`, as `SchemaResult` has it, and `null` for a name the schema doesn't have: an unknown name, or a built-in scalar nothing references.
- **`isOneOf`** (§4.2.2, since September 2025): true for a OneOf input object, false for another input object, null for every other kind. A wrong value for an input object fails `isOneOf`. A non-null `isOneOf` on a type of another kind fails `typeKinds`. Both rest on September 2025.
- **Wrapper types** (§4.2.2): for List and Non-Null, "All other fields must return {null}". The `wrappers` vector must return each of `__Schema`'s fields once, with its type: `[__Type!]!` for `types`, and so on (`Introspection!SchemaFieldsMatch`). `wrappers.user` must return each field of `Resource` the same way (`Introspection!TypeFieldsMatch`, which `SchemaFieldsMatch` is a case of). A field of the service's own is allowed. An empty list, `null`, a field left out or a lost wrapper fails `typeKinds`, so that an empty answer can't pass. Each wrapper among those field types must have a null `name`, `description`, `specifiedByURL`, `fields`, `interfaces`, `possibleTypes`, `enumValues` and `inputFields` (`Introspection!WrapperMatches`). Anything else fails `typeKinds`. A non-null `isOneOf` on a wrapper fails `typeKinds` too, since September 2025.
- **Extending the introspection types:** no sentence of §4 forbids it. The nearest is "Below are the full set of type system definitions providing schema introspection, which are fully defined in the sections below", which has no key word, and Appendix A says "A conforming implementation of GraphQL may provide additional functionality, but must not do so where explicitly disallowed". So a field, argument or enum value an introspection type has beyond the spec's, or an introspection type of the service's own, fails `builtinAdditions`, which is informational. A definition left out or changed still fails `builtinDefinitions`, a MUST. An argument added to a built-in directive is §3.13's, and stays with `builtinDefinitions`.

Every response exercises `envelope` and `executes`. A `__schema` result that has the selected fields exercises every other check but `typeByName`. A lookup result exercises `typeByName` and the checks about a single type, but not `roots`, `types`, `builtinScalars`, `directives` or `builtinDirectives`. The `wrappers` and `wrappers.user` results exercise `typeKinds` only, a probe `directives` and `builtinDirectives` only, and an `emptySelection` result `envelope` and `executes` only. A schema rejected for a directive in `needs` exercises only `builtinDirectives`. Under the October 2021 profile, nothing exercises `isOneOf`, `order` or `defaultValuePrinting`, and only it exercises `deprecationReasonOmitted`. Only the older releases' profiles exercise `builtinEdition`.

Every check in the report has a `basis`, which quotes the sentences of September 2026 it rests on, and says why where the level isn't the key word's. `isOneOf`, `order` and `defaultValuePrinting` carry `"since": "September2025"`, the release that introduced them. No check has `levels`: where October 2021's wording gives a null reason a lower level, that is the separate check `deprecationReasonOmitted`, and under an older release's profile a check's `note` says how that release scopes it.

A crash fails `executes`. A vector with `syntax` (`directiveDeprecation` applies `@deprecated` to a directive definition, and `directiveDefinitionLocation` uses the location `DIRECTIVE_DEFINITION`, which only September 2026's grammar has; `emptySelection` sends empty selection sets, also new in September 2026; `directiveArgDeprecation` deprecates a directive argument and `descriptionText` uses `\u{…}` escapes and raw control characters, which only September 2025's grammar has) that gets a request error, while the probe's query was answered, isn't graded: the implementation follows an older release's grammar. `cases.notGraded` counts those, and `cases.crashed` the crashes.

A result counts toward one finding: the set of problems it has. Problems with the document's types are grouped by aspect, problems with built-ins by the exact field or argument. A finding's `since` counts its results by the release they rest on, and each check's `failingSince` counts the same way, for that check alone. A result rests on a release when every problem behind it does: `@oneOf`, `isOneOf` (including a non-null `isOneOf` outside input objects), order and printing rest on September 2025, and a built-in problem on its label (above); the result rests on the earliest of its problems' releases, and on none if any problem rests on none. It rests no earlier than its vector's `since`: a failure on a vector with `"since": "September2025"` rests on September 2025 at least. A bad envelope, or an answer that isn't the query's result, rests on the vector's `since`. A crash rests on no release, whatever its vector's `since`: it fails in every release. The report's `since` gives, per release, the graded vectors with that `since` and how many of them fail, crashes left out. A finding's example starts with `[since September 2025]` or `[since September 2026]` for a vector with `since`. The run fails on any failing MUST check, a failing SHOULD check with `--strict`, an answer without `response`, or a failed self-test. An informational check never fails the run.

## Vectors

[`kit/introspect/vectors.json`](../../kit/introspect/vectors.json) holds 71 vectors for 21 schemas: 42 `__schema` vectors, each schema with and without `includeDeprecated: true`; 23 lookup vectors, one with `includeDeprecated: true` per schema but `directiveArgDeprecation`, `locations` and `directiveDefinitionLocation` (whose schemas are about directives, which `__type(name:)` doesn't show), one more each without it for `deprecation`, `inputDeprecation`, `interfaceDeprecation` and `inputDeprecationAll`, and `roots.lookup.fragments`; the two wrapper vectors, the two probes and the two `emptySelection` vectors. Each has `queries`, the query of each profile whose release can express its schema. The 16 vectors for `inputDeprecation`, `oneOf`, `inputDeprecationAll`, `directiveArgDeprecation` and `descriptionText` carry `"since": "September2025"` (`Introspection!IsOct2021Schema` is false, or, for `descriptionText`, its strings need September 2025's lexical grammar) and have September 2026's and September 2025's queries; the 7 for `directiveDeprecation`, `directiveDefinitionLocation` and `emptySelection` carry `"since": "September2026"` (`Introspection!IsSep2025Schema` is false, or the request has empty selection sets) and have only September 2026's. The other 48 have all three. The `scalars` vectors have `"needs": ["specifiedBy"]` and the `oneOf` vectors `"needs": ["oneOf"]` (`Introspection!OptionalDirectivesUsed`). The 15 vectors whose schemas declare a directive have `"requires": ["custom-directives"]`. The 12 vectors for `directiveDeprecation`, `directiveArgDeprecation`, `directiveDefinitionLocation`, `descriptionText` and `emptySelection` also have `syntax`, which says why a request error there isn't graded. [`scripts/generate-vectors-introspect.mjs`](../../scripts/generate-vectors-introspect.mjs) writes the file. It checks each schema valid by `TypeSystem!Verdict`, with every default value coercible, then evaluates `Introspection!SchemaResult` with September 2026's built-ins, the query root's name and `Introspection!TypeByName` for each lookup with tla-ts. It does the same with `Sep2025Builtins` and `Oct2021Builtins`, and checks that for a schema an older release can express, the result is September 2026's without the fields that release's query doesn't select. It also reads every string in each schema's SDL with `Lexer.tla`'s `StringValueAt` and stops if the value differs from graphql-js's, so the descriptions and defaults the vectors expect are §2.10.4's values. `--check` regenerates the file and fails if it differs. graphql-js only parses the SDL.

tla-ts can't carry a raw control character, a `\u` escape or a supplementary character in a string. So `run.mjs` and the script pass every string through `toTla` (`data.mjs`) on the way in, which keeps printable ASCII but `%` and writes anything else as `%<hex code point>;`, and `fromTla` on the way out. `IntrospectChecks.tla` reads a printed default value from `printed`, its code points.

Each `__schema` vector's `expected.response` is the response the reference expects, without the built-ins, which every schema shares and the file holds once per profile in `builtins.September2026`, `builtins.September2025` and `builtins.October2021`, each in its profile's shape. Under an older release's profile, a vector's expected response is its `expected` without the fields that release's query doesn't select. The `wrappers` vector's expected answer follows from the built-ins. A lookup vector has `lookups` (`[{ "alias", "name" }]`), and its `expected.response` has the reference's `__Type`, or `null`, under each alias. Each asks for a few of the schema's types, among them a built-in scalar or introspection type, and for `Unknown`. `minimal`, `roots` and `builtinScalars` also ask for a built-in scalar they don't reference, whose answer is `null`. Descriptions the spec leaves open are null. The kit doesn't compare responses with them directly: it evaluates `Matches` or `TypeByNameMatches`, as above. The expected responses are what the self-test starts from and what findings show.

## Limits

- **`__type(name:)` for a few names:** each lookup vector asks for four to six names. The kit doesn't ask for every type, nor for the service's own types.
- **Built-ins compared by name:** the comparison assumes the spec's introspection types, in any order. A field, argument or enum value a service adds fails only `builtinAdditions`, as graphql-js 17's does, and the kit doesn't select it.
- **Missing fields hide what they would show:** a service without, say, `__Type.isOneOf` counts that once, and its `isOneOf` values aren't graded at all. Without a field the kit can't do without (`__Type.kind`, `__Field.type`, `ofType`), only `executes` is graded.
- **One profile per run, from one vector:** the profile is chosen by the answer for `minimal`. An implementation that answers September 2026's query for some schemas but not others is graded against September 2026.
- **Wrapper types of two types only:** the kit selects every field of a List or Non-Null type only in the `wrappers` vectors, for `__Schema`'s fields and `Resource`'s. Elsewhere `TypeRef` selects `kind`, `name` and `ofType`.
- **`@skip` and `@include` are probed on one schema:** the probes only show whether the service honours them on `type Query { a: Int }`. In the other vectors, a service that leaves them out of `directives` fails only the SHOULD `builtinDirectives`.
- **Printing is graded on default values only:** `defaultValuePrinting` reads the strings of `__InputValue.defaultValue`. Descriptions are values, not printed strings, so §2.10.4's rule on producing a StringValue doesn't apply to them. Meta-fields off the query root (§4.2) are left to the validate area: here they are only asked in fragments on the root.
- **`needs` and `syntax` are guesses about the cause:** a request error for a schema in `needs` counts as not providing the directive, and one for a schema with `syntax` as not having September 2026's grammar, provided the same query is answered for `minimal`. The kit doesn't read error messages. A service that drops `@specifiedBy` or `@oneOf` from `directives` and also from its types can't be told apart from one that doesn't provide them: both break only a SHOULD.
- **No extensions:** the schemas have no `extend` definitions, since `TypeSystem.tla`'s data comes from definitions.
